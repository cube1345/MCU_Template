# Agent 工作规范

## 引脚资源文档维护

- 当前工程的引脚分配以 `docs/pin_allocation.md` 为统一记录。
- 修改 Board 层引脚、CubeMX 系统引脚、外设实例或复用功能时，必须在同一次任务中同步更新该文档。
- Platform 后端支持的候选映射不能直接记为已占用；必须结合 Board 配置和 Application 启动路径判断资源状态。
- 删除 Application 任务不等于释放 Board 层预留。只有同步删除或修改 Board 配置后，才能把对应引脚标记为空闲。

本文件适用于 `agent/` 目录及其所有子目录。

## Skill 使用规则

1. 开始任务前，检查 `agent/skills/` 中是否存在适用的 Skill。
2. 当任务与某个 Skill 的说明或触发条件匹配时，必须遵守该 Skill 的规定，并在需要时调用它。
3. 使用 Skill 时，先完整阅读其 `SKILL.md`，再按其中的指引读取必要的 `references/`、执行 `scripts/` 或使用 `assets/`。
4. 多个 Skill 同时适用时，只选择能够完整覆盖任务的最小集合，并遵守它们共同的约束。
5. Skill 的安全边界、验证步骤和强制检查项不得跳过。

## 中英文文档规则

Skill 文档采用以下命名方式：

- 英文版使用正常文件名，例如 `SKILL.md`、`commands.md`。
- 中文版在扩展名前添加 `_zh`，例如 `SKILL_zh.md`、`commands_zh.md`。

AI 默认优先读取英文版。面向人阅读、审阅或交付中文说明时，优先使用中文版。需要确认翻译、中文措辞或两个版本的一致性时，应同时读取中英文版本。

代码块、命令、路径、文件名、API 名称、配置键和协议字段在两个语言版本中必须保持一致，不得翻译或随意改写。

## 版本一致性与同步

1. 修改任一语言版本时，必须检查并同步对应的另一语言版本。
2. 当中英文版本内容不一致时，以最新修改的版本为准，并将其准确同步到另一版本。
3. 判断“最新版本”时，优先依据版本控制中的最后修改记录；对于尚未提交的修改，可依据工作区差异和文件修改时间判断。
4. 同步时应保持语义、章节结构、约束、示例、链接和操作步骤一致，而不是简单复制原语言文本。
5. 如果无法可靠判断哪个版本更新，或两个版本各自包含独立的新内容，不得擅自丢弃任何一侧；应合并全部有效内容，必要时向用户确认。
6. 同步完成后，检查中英文文件是否成对存在，并验证所有本地 Markdown 链接均可访问。

## 优先级

用户的明确要求优先于本文件；本文件优先于一般工作习惯。若具体 Skill 提供了更严格、更具体的规则，则在该 Skill 的适用范围内遵守其规则。

## 注释语言规范

- 默认情况下，所有代码注释必须使用中文书写。
- 注释内容应使用专业、准确、简洁的技术表述，避免口语化、含糊化或冗余描述。
- 除非用户明确要求使用其他语言，禁止在注释中混用英文自然语言说明。
- 宏定义、结构体定义、枚举定义、全局变量、静态全局变量、跨模块可见常量等非函数代码元素，同样必须添加清晰注释，说明其用途、含义、取值单位或使用约束。

## 函数头部注释规范

- 每个对外可见函数、接口函数或具备独立职责的函数，均应在函数定义前添加完整的头部注释。
- 函数头部注释必须采用以下结构与风格：

```c
/**
  * @brief  清晰说明函数的核心功能。
  * @param  参数名：说明参数含义、用途及必要限制。
  * @param  参数名：说明参数含义、用途及必要限制。
  * @retval 说明返回值含义；若无返回值，则写为 None。
  */
```

- 当函数参数存在可选值、取值范围、状态含义或特殊约束时，必须在 `@param` 项下继续补充说明。
- 函数头部注释应重点描述函数职责、参数语义、返回结果及关键限制，不得仅重复函数名本身。
- 注释格式应保持与以下风格一致：

```c
/**
  * @brief
  * @param
  * @retval
  */
```

## 函数内部注释规范

- 函数内部必须根据实现逻辑添加必要注释，不允许仅保留函数头注释而缺少过程说明。
- 对以下内容必须补充行内注释或段落注释：
  - 关键流程控制
  - 状态切换
  - 标志位设置、清除与判断
  - 边界条件、异常分支及兼容性处理
- 函数内部注释应说明“为什么这样做”或“当前步骤的技术目的”，避免无意义地逐行翻译代码。
- 对连续的相关逻辑，优先采用逻辑块注释，确保实现意图清晰可读。

## 宏与全局对象注释规范

- 所有宏定义必须在定义附近补充注释，说明其功能、单位、适用范围或关键限制。
- 所有全局变量、静态全局变量、全局常量及跨文件共享对象，必须在定义附近补充注释。
- 对状态变量、标志变量、计数器、超时阈值、地址常量、缓冲区长度等容易产生歧义的对象，必须明确说明其技术含义。
- 注释重点应说明“这个对象为什么存在、给谁使用、使用时需要注意什么”，不得仅重复名称字面意思。

## 函数命名规范

- 函数命名必须采用下划线命名法（`snake_case`）。
- 命名应遵循模块前缀 + 功能域 + 动作描述的结构，确保语义完整、层次清晰、可直接体现所属模块与操作行为。
- 函数名称应全部使用小写字母，单词之间使用下划线分隔，并保留必要的模块前缀与功能后缀。
- 禁止使用含义模糊、缩写随意、职责不清或无法体现模块归属的命名方式。

## 人类临时调试改动保护规范

- 当 AI 发现代码中存在明显由人类临时测试、调试或验证目的产生的改动，例如临时屏蔽任务创建、暂时注释某段调用、保留调试输出或临时关闭某个功能时，不得仅为了消除 warning 而擅自恢复、删除或重构这些改动。
- 如果这类临时改动只产生不影响程序主要运行路径的 warning，且未造成编译错误、链接错误、明显运行风险或用户当前请求范围内的问题，AI 应保留现场，并在回复中说明 warning 的来源和影响。
- 若确实需要处理 warning，应优先向用户确认该临时改动是否可以被修改；在未获得明确授权前，只能提出建议，不得直接改动相关代码。
- 当 warning 来源不确定是否属于人类临时测试改动时，AI 应通过上下文、注释、最近改动和用户当前目标进行判断；无法可靠判断时，应保守处理，避免破坏用户的调试意图。
