# 结果验证

英文版本：[result-validation.md](result-validation.md)。

使用相互独立的证据。控制台显示 `Build finished` 或 `Application running` 本身不足以
证明成功。

## 构建判断

检查三类证据：

1. 退出码。
2. 构建日志。
3. 输出产物。

常见 uVision 命令行约定为：

| 退出码 | 常见含义 | 处理方式 |
| --- | --- | --- |
| `0` | 构建完成，无警告和错误 | 继续验证 |
| `1` | 构建完成，但存在警告 | 报告警告并验证产物 |
| `2` | 构建错误 | 失败，禁止烧录 |
| `3` | 致命错误 | 失败，禁止烧录 |

如果已安装版本或项目包装脚本定义了不同语义，以它们为准。

尽可能从日志提取：

- Target 和编译器/工具链。
- 错误数和警告数。
- 程序大小：Code、RO-data、RW-data、ZI-data。
- 链接器或 Pack 错误。
- 构建耗时。

要求预期 AXF/HEX 存在，记录完整路径、修改时间和大小。如果预期发生重建但时间戳
没有变化，将产物视为可疑；问题解决前禁止烧录。

## 烧录判断

要求：

- 进程或脚本退出码表示成功。
- 烧录日志存在。
- 工作流包含擦除时，擦除成功。
- 编程成功。
- 校验成功，例如出现 `Verify OK`。

任何阶段失败时，报告第一个失败点，不得声称板卡已成功编程。

`Application running` 表示工具在编程后释放或启动了目标，不能证明显示、串口协议、
外设、控制算法或其他应用功能正确。

## 证据缺失或陈旧

- 日志缺失：即使产物存在，验证仍然失败。
- 产物缺失：在工作流意义上构建失败。
- 构建失败后的旧产物：绝不能用作成功证据。
- 被覆盖的固定日志：只能描述为最近一次运行，不能当作历史记录。
- 并发任务共用同一路径：结果不可靠；应使用独立日志路径或串行执行。
