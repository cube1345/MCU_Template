# Keil 工作流

英文版本及 Codex 正式入口：[SKILL.md](SKILL.md)。

## 语言选择

- 默认读取英文 `.md` 文件。
- 只有在中文措辞、用户意图、翻译核对或英文版本存在歧义时，才读取对应的
  `_zh.md` 文件。
- 默认不要同时加载两种语言版本；它们包含相同规则，同时读取会重复占用上下文。
- 修改稳定规则时，应在同一任务中同步更新中英文版本，确保内容等价。

目标仓库是配置事实来源。不得假设其他项目的路径、Target、器件、输出名、
Flash 算法或调试探针适用于当前项目。

## 强制安全门槛

- 提议或执行 `.bat`、`.cmd`、`.ps1` 前必须读取其内容。
- 根据实际命令判断脚本行为，不得根据 `run`、`verify`、`build` 等名字猜测。
- 对仅构建请求，禁止选择包含 UV4 `-f`、调用烧录脚本或以其他方式写入硬件的脚本。
- 未检查脚本内容前，不得声称它“仅构建”或“只读”。
- 未获得用户明确授权，禁止烧录硬件。

示例：用户只要求验证编译，并提到 `agent/keil/run_keil.bat` 时，先检查该文件。
如果它执行构建加烧录，就拒绝用于本次请求，改用经过验证的纯构建脚本（例如
`build_keil.bat`）或经过验证的 UV4 `-b` 命令。

## 判断请求类型

1. 将请求分成以下动作：
   - **构建**：编译、链接并验证产物，不接触硬件。
   - **烧录**：把已确认的现有产物写入硬件。
   - **构建并烧录**：先构建，构建干净通过后才烧录。
   - **调试或运行会话**：除非项目文档明确如此定义，否则不能当作构建并烧录。
2. 对“验证一下”“检查固件”等含糊请求，默认只构建。
3. 用户明确说烧录、下载、编程或构建并烧录，即视为对应范围的授权；否则在烧录前
   停止并请求批准。

## 发现项目工作流

1. 如果存在项目级 AI 索引，先读取最近的 `agent/readme.md`、
   `agent/agent_readme.md` 或对应中文版本。
2. 如果存在项目自己的 `agent/keil/`，读取其中的文档和脚本。
3. 找到目标 `.uvprojx`、Target、Keil 可执行文件、输出产物和日志路径。烧录时还要
   检查器件、探针/下载器、Flash 算法和地址范围。
4. 优先使用已经验证过的项目脚本，不要临时拼接新命令。
5. 完整预检清单见
   [references/project-discovery_zh.md](references/project-discovery_zh.md)。

## 执行最小且安全的工作流

1. 执行前检查候选脚本，并根据实际命令分类。
2. 对仅构建请求，只运行不可能烧录的命令或脚本。拒绝任何包含 UV4 `-f` 或调用
   其他烧录脚本的候选项。不能因为存在 `run_keil.bat` 就把它用于构建验证。
3. 烧录前确认产物属于目标项目，并且对本次请求而言足够新。
4. 构建并烧录必须串行进行；构建失败、日志缺失、产物缺失或产物陈旧时禁止烧录。
5. 立即保存真实进程退出码。在 PowerShell 中，必须在运行其他原生命令前保存
   `$LASTEXITCODE`。
6. UV4 命令、停止条件和动作检查见
   [references/workflows_zh.md](references/workflows_zh.md)。
7. Windows 调用、引号、编码和输出处理见
   [references/windows-powershell_zh.md](references/windows-powershell_zh.md)。

## 独立验证

不得只相信成功提示。必须验证：

- 进程或脚本退出码。
- 构建日志中的错误和警告数，或烧录日志中的擦除、编程和校验状态。
- 预期 AXF/HEX 是否存在，以及时间戳和大小。

判断规则见 [references/result-validation_zh.md](references/result-validation_zh.md)。
每次写入硬件前必须读取
[references/flashing-safety_zh.md](references/flashing-safety_zh.md)。

## 报告结果

报告以下内容：

- 实际执行的脚本或命令。
- 选择的工程和 Target。
- 构建错误数和警告数。
- 可用时报告产物路径、时间戳和大小。
- 是否跳过、尝试、验证或未能完成烧录。
- 第一个阻塞性失败和对应日志路径。
- 尚未验证的硬件、工具链或项目假设。

不能因为 Keil 显示 `Application running` 就声称固件功能正常。它只能证明编程后
目标被启动，不能证明应用行为正确。任务要求运行验证时，应使用串口输出、调试器状态
或明确的功能检查。

当项目特定的 Keil 路径、Target、工作流或故障排查规则发生稳定变化时，更新目标项目
中负责该知识的文档。不要把瞬时日志、一次性观察或项目绝对路径写进本 Skill。
