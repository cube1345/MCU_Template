# C 语言工程化面向对象

以明确的对象布局、受控的依赖关系、MCU 硬件边界和最小必要抽象构建嵌入式 C 系统。将 OOP 当作工程工具，而不是全项目强制要求。

## 工作流程

1. 检查仓库规则、编译器/链接器约束、RTOS 模型、内存策略、错误模型、初始化顺序及邻近模块的惯例。
2. 当只有一个稳定实现且没有有价值的替换边界时，保留带统一前缀的普通 C 模块。
3. 仅为可互换实现增加“基类 + const 操作表”。用板级绑定隐藏硬件选择；跨 MCU/SDK 边界时增加平台接口；仅在确实降低耦合时使用注册表或初始化段。
4. 在编写后端之前，定义所有权、生命周期、有效状态、必需/可选操作、回调上下文、阻塞行为、线程/ISR 安全性和错误语义。
5. 实现一条垂直路径：接口 -> 具体 MCU 后端 -> 板级绑定 -> 目标构建与板级冒烟测试。
6. 完成前阅读 `references/review-checklist_zh.md`。

## 工程规则

- 当项目惯例与此通用流程冲突时，优先遵守项目惯例。
- 优先使用静态或调用方持有的存储。除非项目策略允许且所有权/耗尽行为明确，否则不要引入堆分配。
- 保持公共头文件精简；辅助函数、具体对象和操作表应文件私有并使用 `static`。
- 用指定初始化器将不可变操作表定义为 `static const`。
- 初始化时绑定操作表。没有明确且同步的策略替换需求时，不要在运行期修改它。
- 默认将基类嵌入为子类的第一个成员。使用 `&child.base` 向上转型；使用项目的 `container_of` 实现向下转型。
- 应用代码只暴露和使用基类/接口句柄。具体类型、引脚/通道/地址数据和厂商 SDK 类型应留在板级或架构后端代码中。
- 将 HAL/寄存器访问限制在具体驱动或平台后端；绝不让 HAL 类型泄露进基类或应用 API。
- 在边界校验外部输入，并在调试构建中断言内部不变量。对可恢复失败保留发布构建中的错误路径。
- 初始化时校验必需操作。对可选操作，返回有文档说明的不支持错误，或实现有文档说明的默认行为；绝不伪造成功。
- 传播有意义的项目错误码，不要静默丢弃失败。
- 为每个公共 API 记录所有权、回调上下文、锁、阻塞和 ISR 限制。仅使用 `volatile` 并不能实现同步。
- 避免深层继承和隐藏的可变全局状态。多个实例可以共存时，优先使用组合和每设备操作对象。
- 不要在生产代码中加入教学性日志或教程注释。

## 输出要求

实现时，说明为什么需要 OOP、抽象边界在哪里，并按接口/后端/绑定/测试归类改动及说明已验证内容。评审时，优先检查生命周期、布局、分派、错误、并发和硬件边界缺陷；指出不必要的抽象。
