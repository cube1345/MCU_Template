# 工程评审清单

## 抽象是否合适

- 替换性、可移植性或可测试性是否确实是需求？
- 普通 C 模块是否会更简单且足够？
- 继承是否仅限于一个嵌入式基类，并通过组合实现独立行为？

## API 与分派

- 公共符号是否有前缀，头文件是否精简且可独立包含？
- 辅助函数、具体实例和操作表是否私有且使用 `static`？
- 应用代码是否只使用基类/接口句柄？
- 可复用驱动 API 中是否没有厂商 SDK 类型？
- 默认情况下基类是否位于首成员，是否用 `&child.base` 向上转型，并用 `container_of` 向下转型？
- 操作表是否为 `static const`、使用指定初始化器，并在初始化时校验？
- 包装层是否集中执行状态检查和分派策略？
- 多个实例能否运行而不会产生非预期共享状态？

## 生命周期、错误与并发

- 存储所有权是否明确，且是否遵守堆使用策略？
- 是否定义了初始化、部分失败、重试、反初始化和逆序清理？
- 是否校验外部输入，并安全地断言内部不变量？
- 是否传播有意义的错误，而不是静默成功？
- 是否记录了回调上下文、线程/ISR 安全性、阻塞行为和同步方式？是否避免把 `volatile` 作为唯一同步机制？

## 平台与验证

- HAL/寄存器调用是否限制在具体驱动或平台后端中？
- 可复用基类和应用 API 中是否没有厂商 HAL 类型？
- 启动顺序是否明确、可防重复执行并检查错误？
- 如果使用链接段，是否验证了边界、LTO、段垃圾回收和工具链？
- 代码是否使用仓库的严格告警选项编译，并具有目标构建、烧录或板级冒烟测试路径？是否报告了尚未验证的硬件路径？
